# Wardrobe AI 技术架构说明（小白版）

> 面向：未系统接触过 Web / 后端 / AI 工程的读者  
> 目标：用生活类比讲清「系统由哪些部分组成、各自干什么、为什么这样选」  
> 阅读后你应能回答：用户点一下按钮，数据大概会经过哪些服务？

---

## 1. 先建立一张「总地图」

把整个项目想成一家**线上衣橱店**：

| 生活角色 | 项目里的组件 | 一句话职责 |
|---|---|---|
| 店面橱窗 + 收银员 | **Next.js**（网站） | 你看到的页面；也负责把请求转给后面的服务 |
| 会员办卡台 | **Supabase Auth**（登录认证） | 注册、登录、判断「你是谁」 |
| 账本 / 货架台账 | **PostgreSQL**（数据库） | 存衣物信息、标签、统计等「文字数据」 |
| 仓库货架 | **MinIO**（图片仓库） | 专门存衣物照片等大文件 |
| AI 鉴定师 | **FastAPI + AI 模型** | 看图识别颜色、分类等属性 |
| 物业总控 | **Docker Compose** | 一键把上面这些服务在本机「租好房并开门」 |

它们默认都跑在你电脑上（本地开发），通过「端口号」互相访问，就像同一栋楼的不同房间号。

### 1.1 一张简化架构图

```text
你（浏览器）
    │
    ▼
┌──────────────────┐
│     Next.js      │  页面 + 接口中转（BFF）
│  端口通常 :3000   │
└────────┬─────────┘
         │
    ┌────┼──────────────┬────────────────┐
    ▼    ▼              ▼                ▼
 登录认证  数据库写衣物   上传/读图片      调用 AI 识别
(Supabase) (PostgreSQL)   (MinIO)        (FastAPI)
 经 Kong 网关 :8000        :9000            :8001
```

**BFF** 是什么？  
Backend For Frontend：前端网站自己带一层「小后端」。好处是浏览器只跟 Next.js 说话，密钥、内部地址不必暴露给用户。

## 2. 各层选型与原因

### 2.1 网站：Next.js + TypeScript + Tailwind + shadcn/ui

| 选型 | 它是什么 | 为什么选它 |
|---|---|---|
| **Next.js** | 基于 React 的全栈框架 | 一套代码既能做页面，又能写接口；SSR（服务端渲染）对登录态友好；社区与 AI 相关示例多 |
| **TypeScript** | 带类型的 JavaScript | 衣物字段、API 返回值写清楚类型，减少「字段拼错却运行到一半才炸」 |
| **Tailwind CSS** | 用 class 拼样式 | 改 UI 快，团队风格统一 |
| **shadcn/ui** | 可复制进项目的组件库 | 登录框、按钮、表单不用从零画，且代码在你仓库里可控 |

**为什么不选「纯前端 Vue + 另起 ASP.NET 后端」？**  
早期设想里出现过那套组合，但当前 MVP 设计已统一为 Next.js：一个人/小团队时，少维护一套独立后端语言与仓库边界，交付更快。

### 2.2 登录与数据：自托管 Supabase 组件

我们**不是**必须用云上的 Supabase 官网服务，而是用 Docker 在本地搭同类能力：

| 组件 | 作用 | 为什么需要 |
|---|---|---|
| **PostgreSQL** | 关系型数据库 | 衣物、标签、用户关联适合表格存储与查询 |
| **GoTrue（Auth）** | 认证服务 | 成熟的邮箱密码登录、JWT 会话，不用自研加密登录 |
| **PostgREST** | 把数据库变成 HTTP API | 后续查询可走标准接口 |
| **Kong** | API 网关 | 把认证、数据库 API 统一挂在 `localhost:8000` 下，前端只记一个地址 |

**为什么选这套，而不是自己写一套登录 + 手写全部 SQL 接口？**

1. **认证很难写对**（密码哈希、会话、过期刷新）。用现成 Auth 更安全。  
2. **本地自托管**：开发阶段少依赖外网账号与账单。  
3. **和「线上对象存储 / JWT」习惯一致**，以后若上云，心智模型可复用。

**注意：** 仓库里的 `.env` / `.env.example` 里的 `ANON_KEY`、`JWT_SECRET` 等若仍是占位符，登录会失败。真实联调前必须换成与本地 Auth 匹配的密钥（见测试指导文档）。

### 2.3 图片：MinIO（而不是直接塞进数据库）

| 选型 | 原因 |
|---|---|
| **MinIO** | 兼容亚马逊 S3 协议的对象存储；本地 Docker 就能跑 |
| 数据库只存 **图片 URL** | 数据库擅长结构化文字；大图塞库会又慢又难备份 |

**类比：** 账本上写「仓库货架 A-12」，照片实体放在仓库，而不是把照片夹进账本里。

路径习惯类似：`http://localhost:9000/wardrobe-images/{用户ID}/{随机文件名}.jpg`

### 2.4 AI：独立 FastAPI 服务 + 可切换模型

| 选型 | 原因 |
|---|---|
| **Python FastAPI** | AI / 图像相关生态以 Python 最成熟；接口写起来简单 |
| **与 Next.js 分开部署** | AI 慢、吃资源；挂了不应拖垮整个网站；以后可单独扩容 |
| **策略模式：Ollama / 阿里百炼** | 本机用 Ollama 免费试；生产可用云端视觉模型；通过环境变量 `MODEL` 切换，业务代码少改 |

**数据流（识别一次衣服）：**

1. 浏览器把图片交给 Next.js  
2. Next.js 先把图存进 MinIO，得到 URL  
3. Next.js 再请求 FastAPI「请识别这张图」  
4. FastAPI 调 Ollama 或百炼，返回分类、颜色等字段  
5. 前端把结果填进表单，用户确认后写入数据库  

阶段二目前只做到「上传进 MinIO」；完整 AI 桥接在阶段三。

### 2.5 编排：Docker Compose

| 选型 | 原因 |
|---|---|
| **Docker** | 把「装 Postgres、装 MinIO……」变成「拉镜像 → 启动」，减少「在我电脑上能跑你电脑不行」 |
| **Compose** | 一份 `docker-compose.yml` 描述多服务依赖与端口，一条命令启动/停止 |

你不需要一开始就精通 Docker，只要记住：

- `docker compose up -d` ≈ 开门营业  
- `docker compose ps` ≈ 看哪些店还开着  
- `docker compose logs -f 某服务名` ≈ 看监控录像找故障

## 3. 请求怎么走（按场景）

### 3.1 未登录访问衣柜

1. 打开 `http://localhost:3000/wardrobe`  
2. Next.js 的 **middleware（中间件）** 检查有没有有效登录态  
3. 没有 → 跳到 `/auth/login`  

### 3.2 注册 / 登录

1. 用户在登录页提交邮箱密码  
2. 浏览器端 Supabase 客户端请求 Auth（经 Kong）  
3. 成功后写入 Cookie / Session  
4. 再访问受保护页面即可通过  

### 3.3 保存一件带图的衣物（完整版，后续阶段）

1. 上传图片 → MinIO → 得到 `image_url`  
2.（可选）AI 识别 → FastAPI → 预填属性  
3. 用户确认表单 → Next.js API → PostgreSQL 写入 `clothing_items`  
4. 列表页再从数据库读出来展示

## 4. 仓库目录怎么对应到架构

```text
Wardrobe AI/
├── docker-compose.yml      # 总开关：启动各服务
├── kong.yml                # 网关路由配置
├── .env / .env.example     # 密钥与地址（勿把真密钥提交到公开仓库）
├── nextjs/                 # 网站 + BFF
│   ├── app/                # 页面与 API Routes
│   ├── components/         # UI 组件
│   ├── lib/supabase/       # 登录客户端
│   ├── lib/minio.ts        # 图片上传
│   └── middleware.ts       # 路由守卫
├── fastapi/                # AI 识别服务
├── supabase/migrations/    # 数据库表结构 SQL
└── docs/                   # 说明文档（含本文）
```

## 5. 常见端口一览（本地）

| 端口 | 服务 | 你何时用到 |
|---|---|---|
| **3000** | Next.js 网站 | 浏览器日常访问 |
| **8000** | Kong（Supabase 入口） | 前端配置的 `NEXT_PUBLIC_SUPABASE_URL` |
| **9000** | MinIO API | 图片 URL、上传 |
| **9001** | MinIO 控制台 | 可视化看桶里有哪些文件 |
| **8001** | FastAPI | AI 健康检查 / 识别接口 |
| **5432** | PostgreSQL | 一般不用直接碰，给高级排查用 |
| **11434** | Ollama | 本地模型（若启用） |

## 6. 架构决策小结（背这几句就够）

1. **一个网站入口（Next.js）**：降低全栈协作成本。  
2. **认证与结构化数据交给 Postgres + Auth**：安全与查询可靠。  
3. **图片进对象存储（MinIO）**：和大文件解耦，路径贴近线上 S3。  
4. **AI 独立成服务**：可替换模型、可单独扩缩容。  
5. **全部容器化**：本机环境可复现，减少「装环境」时间。
